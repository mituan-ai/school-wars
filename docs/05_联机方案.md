# 校园战争 v0.3：四人联机方案

> 场景：四个不在美国的朋友一起玩，服务器在洛杉矶（下称 LA），玩家到 LA 的往返延迟约 220 ms。
> 要求：建房时明确选择"服务器模式"或"玩家主机模式"；两种都能实际使用；重点是操作响应、状态一致、连接稳定，以及直连失败、掉线、房主退出时的处理。单机功能保持不变。

## 1. 现有架构对联机意味着什么

| 现状 | 对联机的意义 |
|---|---|
| `src/core/` 是确定性的纯逻辑，固定 18 tick/s，随机数带种子并保存在状态里 | 可以只同步**指令**，不同步状态：同样的初始种子 + 同样的"第几帧执行哪些指令"，每台机器算出同一局 |
| 核心里只用加减乘除、`Math.floor/abs/sqrt/imul`，没有 `sin/cos/pow` 这类各浏览器实现可能不同的函数 | Chrome、Firefox、Safari、Node 算出的结果应当逐位相同。仍然要做状态指纹校验兜底 |
| 电脑 AI 在 `step()` 内部运行，只读状态和种子随机数 | AI 的决定每台机器都能算出来，不用在网上传 |
| `serializeGame` 已能把整局存成约 49 KB 的 JSON，`hashGame` 约 0.8 ms | 直接用作重连快照和一致性校验 |
| 每 tick 模拟平均约 0.03 ms（4 个困难电脑，p99 约 0.27 ms） | 客户端每帧从"已确认状态"重算几帧到二十几帧预测完全负担得起 |
| **问题**：`g.user_col`（本机玩家是谁）参与了模拟：跳过 AI、经典规则的"众矢之的"豁免、胜负结果、集结点 | 联机时每台机器的座位不同，必须把"谁是人类"放进共享状态（`rules.ai[col] = 'human'`），`user_col` 在联机局里统一为 4（观战位），本机座位只留在界面层 |
| **问题**：编队保存在 `g.groups` 里，会进存档和指纹 | 联机时编队只存在本机界面里，不写进共享状态 |
| `structuredClone` 一份状态约 1 ms | 写一个专用的快速克隆（预测每秒要做几十次） |

## 2. 同步模型：带预测的"权威时间线"指令同步

两种模式用**同一套同步协议**，区别只在"权威"（authority）跑在哪里、玩家怎么连到它：

```
服务器模式：  玩家 ⇄ WebSocket ⇄ [LA：房间 + 权威]
玩家主机模式：玩家 ⇄ WebRTC 直连 ⇄ [房主浏览器：权威]      LA 只做房间、信令、兜底中转
```

**权威**只做三件事：

1. 按自己的时钟每 55.6 ms 关闭一帧，把这一帧要执行的指令打包广播（`batch`）。**它不等任何玩家**，所以一个人卡顿不会让其他人一起卡。
2. 给收到的指令定帧：玩家希望在第 `want` 帧执行；如果第 `want` 帧还没关闭就照办，已经过了就放进当前帧（迟到）。指令里的阵营由权威按连接的座位填写，玩家不能替别人下令。
3. 自己也跑一份模拟，用来：比对各玩家上报的状态指纹、给掉线重连或校验不一致的玩家发快照、处理掉线托管。

**客户端**：

- 保存"已确认状态"：只应用权威发来的帧。
- 估计权威当前在第几帧（ping/pong 对时，取延迟最低的样本），把画面放在"权威当前帧 + 单程延迟 + 余量"的位置，并从已确认状态往前**预测**几帧。预测时自己尚未确认的指令已经算在里面，其他玩家的未知指令当作没有。
- 结果：**自己的指令下一帧就动**（不用等 220 ms 往返）。别人的指令到达时，那几个单位的位置会被纠正，纠正量是几帧的移动距离（单位每帧走 1–2 像素，6 帧约半个小格），用位置平滑把跳动化开。
- 打斗、击倒等特效取自预测；本部沦陷、出局、胜负等重要提示只取自已确认状态，不会误报。

**为什么不选其他做法**：

| 做法 | 不选的原因 |
|---|---|
| 服务器跑模拟、每帧广播完整状态 | 49 KB × 18 次/秒 × 4 人，带宽太大；增量同步要给每个字段写差分，维护成本高，还是要等往返才看到自己的单位动 |
| 经典锁步（所有人收齐指令才走下一帧） | 最慢的人决定所有人的速度，有人掉线全场冻结；220 ms 往返下每个操作都要等约 300 ms |
| 完整回滚网络（GGPO） | 状态小、模拟便宜，本方案的"每帧从已确认状态重算预测"已经得到回滚的主要好处，但实现简单得多 |

### 延迟预算（往返 220 ms）

| | 服务器模式 | 玩家主机模式（假设到房主往返 60 ms） |
|---|---|---|
| 自己的指令在本机画面上生效 | 下一帧（≤ 56 ms），预测 | 同左 |
| 指令被权威确认、在本机定格 | 约 220–280 ms | 约 60–110 ms |
| 其他玩家看到我的指令 | 约 330 ms，伴随几帧位置纠正 | 约 120–170 ms，纠正更小 |
| 房主本人 | — | 延迟约 0（房主有轻微先手，朋友局可以接受） |

## 3. 两种模式的取舍

| | 服务器模式 | 玩家主机模式 |
|---|---|---|
| 对局数据走向 | 全部经过 LA | 优先玩家 ↔ 房主直连，不绕美国；直连失败的人经 LA 中转 |
| 延迟 | 固定约 220 ms 往返，人人公平 | 取决于玩家之间的网络，同城 / 同国通常远好于 220 ms |
| 稳定性 | LA 服务器在线就在，任何玩家掉线都不影响别人 | 房主网络或电脑出问题会触发房主切换，对局暂停几秒 |
| 公平 | 所有人同样延迟 | 房主几乎零延迟 |
| 作弊 | 权威在服务器，较难作弊 | 房主理论上能改自己的客户端；朋友局不处理 |
| 资源 | 服务器跑模拟（很省） | 服务器只转发信令和少量中转 |

**怎么选**：在房间大厅里，每个人到 LA 的延迟、每两个人之间的直连延迟和连通情况都会显示出来。直连普遍明显快于 220 ms 就选玩家主机模式，否则选服务器模式。建房时选定模式，开局前房主还可以根据测得的数据改。

## 4. 连接、掉线与房主退出

| 情况 | 处理 |
|---|---|
| **直连失败**（对称 NAT、运营商限制、STUN 不通） | 大厅里就开始尝试 WebRTC 直连（全员两两互连，用于测速和房主切换）。10 秒内连不上，这对玩家的数据改为经 LA 的 WebSocket 中转，界面标"中转"。不部署 TURN 服务器：中转复用已有的 WebSocket，不必再开 UDP 端口 |
| **STUN** | 同时配置 Cloudflare、Google、小米的公共 STUN，任一可用即可。在中国大陆，Google 的通常不通 |
| **玩家短暂掉线 / 刷新页面** | 按标签页保存的身份令牌自动重连回原座位。权威保留全部帧记录，客户端还有状态就补发缺的帧，页面刷新过就发快照 |
| **静默断网**（网线拔了、Wi-Fi 掉了，没有断开通知） | LA 每 5 秒发一次心跳，两次没回就断开；浏览器发给 LA 的 ping 8 秒没回也主动断开重连。玩家主机模式里经中转的链路没有断开通知，客户端 5 秒收不到权威的任何消息就重新接一次 |
| **玩家掉线超过 15 秒** | 权威在某一帧插入"托管"指令，该校由电脑接管（难度建房时设定，默认普通）；回来后在某一帧交还。托管切换本身也是一条按帧执行的指令，所以所有人一致 |
| **画面落后**（切到后台、卡顿） | 权威不等人。回到前台时一次性追上（每帧约 0.03 ms，追 1 分钟约 30 ms）。预测最多领先已确认状态 24 帧（约 1.3 秒，经 LA 中转的玩家主机模式往返可达 450–500 ms），再多就停住，画面显示"网络卡顿" |
| **状态不一致** | 每 5 秒上报一次已确认状态的指纹，权威比对；不一致就发快照覆盖，并计数显示 |
| **房主退出（玩家主机模式）** | LA 发现房主断开后选出新房主：已连上直连链路最多的在线玩家，同数时选座位号最小的。新房主用自己的已确认状态启动权威，其他人把手里最近的帧记录和未确认指令交给它，补齐后继续；原房主的学校交给电脑。对局暂停约 2–10 秒 |
| **房主刷新页面** | 权威随页面一起没了。重连时浏览器告诉 LA "本页没有在跑这一局的权威"，LA 立即换人（不等 4 秒），原房主作为普通成员回到对局。房间里只剩房主一人时没人可换，只能从头开始 |
| **LA 服务器重启** | 服务器模式的对局丢失（状态只在内存里）。玩家主机模式下对局本身不受影响，但房主切换、中转和重连需要服务器 |
| **房主标签页切到后台** | 浏览器会把后台页面的定时器降到每秒一次。权威的时钟改由 Web Worker 驱动以减轻影响，仍建议房主不要长时间切走 |
| **版本不一致** | 确定性要求所有人运行同一版本。连接时比对构建号，不一致就提示刷新页面 |

## 5. 联机局里的规则差异

- 没有暂停、倍速、存档读档；编队只存在本机。
- 自己的学校出局后可以继续观战；最后只剩一所学校时结束，回到房间大厅可以再来一局。
- 空座位由电脑补上，难度可选；最多 4 名玩家，另可有 2 名观战者。

## 6. 实现清单

| 模块 | 内容 |
|---|---|
| `src/core` | `rules.ai[col] = 'human'`；集结点指令带阵营；托管指令 `control`；快速克隆 `cloneGame` |
| `src/net/protocol.ts` | 消息定义、指令校验、构建号 |
| `src/net/authority.ts` | 权威：定帧、广播、自带模拟、指纹比对、快照、掉线托管、房主切换时接收帧记录。不依赖浏览器和 Node，可在两边运行 |
| `src/net/client.ts` | 已确认状态、预测、对时、迟到自适应、位置平滑、重连 |
| `src/net/link.ts` | 统一的消息管道：WebSocket、WebRTC DataChannel（大消息分片）、服务器中转、本机回环、测试用的模拟网络（可设延迟与抖动） |
| `src/net/session.ts`、`src/net/rtc.ts` | 浏览器端：连接 LA、房间状态、全员两两 WebRTC 测速、组装对局链路、换房主 |
| `server/` | Node：HTTP + WebSocket（`ws`）、房间、信令、中转、服务器模式的权威 |
| `src/ui` | 标题画面"联机对战"、建房 / 加入、房间大厅（座位、电脑难度、规则、模式、延迟矩阵）、对局内连接状态、掉线 / 托管 / 房主切换提示 |
| 部署 | nginx 把 `/net` 反代到本机 Node 服务（systemd）；不动 443 |

## 7. 验收

1. **一致性**：模拟网络下 4 个客户端，每条链路 110 ms 单程、±30 ms 抖动，各自随机下令，跑 10 分钟游戏时间，所有人与权威的状态指纹始终一致。
2. **响应**：服务器模式下，自己的指令在本机下一帧生效；确认延迟中位数不超过往返延迟 + 2 帧。
3. **掉线**：中途断开一人 → 15 秒后电脑接管 → 重连回来交还，全程一致；刷新页面后靠快照回到原座位。
4. **房主退出**：玩家主机模式下关闭房主页面，其余三人在 10 秒内恢复对局，状态一致。
5. **直连失败**：强制禁用 WebRTC 时自动改为中转，可以正常完成对局。
6. **真实运行**：本机起服务，4 个浏览器页面分别跑两种模式，完成开局、下令、掉线、房主切换。
7. **部署后**：在 LA 服务器上实测两种模式（部署前先征得同意）。

## 8. 实现状态（v0.3.0）

### 已实现

- 两种模式都能从建房走到终局：建房时选模式（开局前房主可改），4 个座位可坐人或放电脑（新规则：简单 / 普通 / 困难；经典规则：原版电脑），掉线托管的电脑难度可选，最多 2 名观战者，邀请链接 `?room=CODE`。
- 大厅里显示每人到 LA 的延迟、每两人之间是直连还是中转及其延迟，并按测得的数据建议用哪种模式。
- 对局内：本机预测、位置平滑、连接状态一行字（服务器 / 直连 / 中转 + 往返延迟、你是房主、网络卡顿、等待其他人）、掉线 / 电脑代管标签、离开对局、回到房间、继续观看。
- 断线重连、刷新页面回到原座位、15 秒后电脑托管与交还、主动离开立即托管、直连失败改中转、房主断开或离开后换房主、房主刷新页面后立即换人、状态指纹校验与快照纠正、版本不一致提示。
- 单机功能不变：经典规则的逐帧指纹测试照常通过；单机开局、存档、倍速、暂停照旧。

### 已验证

**自动测试**（`npm test`，共 90 项，全部通过）：

- `tests/net.test.ts`（17 项）：虚拟时钟 + 模拟网络。四名玩家、每条链路单程 110 ms ± 30 ms，随机下令 10 分钟游戏时间，所有人与权威的指纹一致；自己的指令下一帧就在本机生效，确认延迟中位数不超过往返 + 抖动 + 2 帧；15 秒托管与交还、刷新页面、主动离开、状态被改坏后 5 秒内纠正、刷屏限速、不能指挥别人、观战、换房主（含新房主落后时从别人那里补帧）、权威悄悄消失时客户端能察觉。
- `tests/hub.test.ts`（8 项）：LA 服务器的房间逻辑。构建号校验，建房 / 加入 / 换座位，只有创建者能改设置和开局，对局中加入只能观战；服务器模式下两名玩家 + 两台电脑跑 1 分钟后一致、断网重连后追上；掉线 15 秒托管；换房主按"直连最多、座位最小"选人，房主离开对局立即换人，房主闪断回来保留房主、刷新过页面立即换人；信令和中转只在同房间成员之间转发；大厅掉线 30 秒移出。

**浏览器端到端**（本机：Node 服务器每个方向加 110 ms 延迟，即到"LA"往返约 220 ms；Vite 开发服务器；Chromium 无头浏览器，每个玩家一个独立的浏览器上下文；用脚本随机下令，每 90 帧记录一次已确认状态的指纹，最后逐帧比对）：

| 场景 | 结果 |
|---|---|
| 服务器模式，3 人 + 1 台困难电脑 / 4 人 | 往返 227–260 ms；确认延迟单次采样 255–540 ms；每次 14–15 个比对点全部一致，没有快照纠正 |
| 服务器模式，刷新页面 | 0.7 秒回到对局 |
| 服务器模式，断网 25 秒后恢复 | 约 10 秒判定掉线，约 25 秒电脑接管；恢复网络后几秒内交还，状态一致 |
| 玩家主机模式，4 人：2 人直连、1 人直连 + 40 ms 延迟、1 人强制中转（`?relay=1`） | 直连往返 12–13 ms，确认约 50 ms；加 40 ms 延迟者往返约 46 ms，确认约 100 ms；中转者往返 450–530 ms，确认 500–750 ms |
| 玩家主机模式，关闭房主页面 | 5.9–6.3 秒后由直连最多的人接任，对局继续，原房主的学校先显示掉线、15 秒后由电脑接管，状态一致 |
| 玩家主机模式，房主刷新页面 | 2.3 秒后恢复，换了房主，原房主作为普通成员回到对局，状态一致 |
| 单机 | 开局正常，18 帧 / 秒；手机宽度（390 px）下大厅无横向滚动 |

### 仍有限制

- **还没有在真实网络上测过**：没有部署到 LA，也没有跨地区、跨运营商的真实玩家。上面的"直连"都是同一台机器上的 WebRTC，真实网络下的直连成功率（对称 NAT、校园网、移动网络）未知。
- **没有 TURN**：直连不上的玩家经 LA 中转，往返是"他到 LA + 房主到 LA"，约 440 ms 以上，比服务器模式还慢。大厅的建议会把这种情况算进去。
- **只测了 Chromium**：Firefox、Safari 上的确定性按设计应当一致（核心不用 `sin/cos/pow`），但没有实测；万一不一致，指纹校验会发现并用快照纠正，代价是画面跳一下。
- **静默断网时托管偏慢**：要先约 10 秒判定掉线，再等 15 秒宽限期，合计约 25 秒。关页面是 15 秒，点"离开对局"是立即。
- **换房主时对局暂停**：房主断开要等 4 秒确认（避免网络抖一下就换人），实测共约 6 秒；房主刷新页面约 2 秒。房间里只剩房主一人时无人可换。
- **LA 服务器重启**会丢掉服务器模式的对局；玩家主机模式下对局本身不受影响，但期间无法重连、中转和换房主。
- **房主优势**：玩家主机模式下房主几乎零延迟，也有能力改自己的客户端作弊；朋友局不处理。
- **别人的单位会被纠正**：预测里不知道别人的新指令，指令到达时那几个单位会被拉回正确位置（几帧的移动距离），用 90 ms 平滑化开，但仍看得出来。往返越大越明显。
- **后台标签页**：房主的权威时钟由 Web Worker 驱动，按规范不受后台定时器节流影响，但没有在真实浏览器里长时间切后台实测。
- 联机局没有暂停、倍速、存档；编队只存在本机。
